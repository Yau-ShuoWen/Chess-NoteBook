# 棋谱导出与合并设计

## 1. 目标与边界

导出功能首先解决三件事：

1. 不依赖服务器，把手机里的棋谱完整备份到用户选择的位置。
2. 可以只分享或迁移某一个棋谱，也可以一次备份全部棋谱。
3. 从多个导出文件导入时能够合并分支，并且不静默覆盖已有内容。

第一版不把导出文件当作给人直接阅读的棋谱，也不加入账号、云同步、定时备份、图片附件和跨设备实时同步。

## 2. 核心结论

### 2.1 同时支持“单个导出”和“全部导出”

两种入口都需要，但底层使用同一种文件结构：

- 棋谱详情页：`导出这个棋谱`
- 棋谱列表页：`导出全部棋谱`

单个文件中 `documents` 只有一个元素，全部导出时则包含当前所有棋谱。这样导入、校验、版本升级只需要维护一套逻辑，也允许将来导出用户勾选的若干棋谱。

### 2.2 主格式使用专用扩展名，内容采用 JSON

建议扩展名：`.chessnote`

建议 MIME 类型：`application/vnd.shuowen.chess-notebook+json`

文件本质是 UTF-8 JSON，但不直接命名为 `.json`：

- 专用扩展名可以明确表示“这是本应用可恢复的备份”，减少用户误改。
- JSON 便于调试、长期迁移和人工抢救数据，不需要额外引入压缩库。
- 当前没有图片等二进制附件，使用 ZIP 只会增加实现和排错成本。

若以后节点支持图片或音频，再升级为压缩包容器；旧版 JSON 文件仍应保持可导入。

### 2.3 纯文本不作为备份格式

纯文本会丢失稳定标识、层级信息、字段版本和合并依据。PGN 虽然能表达主线、变化和注释，但应用里的节点名称、文档说明、当前录入位置等数据不能保证无损往返。

因此格式分工为：

- `.chessnote`：备份、恢复、迁移、合并，必须无损。
- `.pgn`：以后作为“分享给棋类软件”的可选导出，不承诺再次导入后完全还原。
- `.txt`：不提供，避免出现一个看起来简单但无法可靠恢复的格式。

## 3. 文件结构

导出文件包含文件级信息和棋谱数组。示意结构如下：

```json
{
  "format": "chess-notebook",
  "version": 1,
  "exportedAt": "2026-10-04T13:20:00+08:00",
  "appVersion": "1.0",
  "documents": [
    {
      "id": "文档 UUID",
      "name": "伦敦体系",
      "description": "视频课程记录",
      "currentPath": ["d2-d4", "d7-d5"],
      "root": {
        "label": null,
        "analysis": null,
        "children": [
          {
            "move": {
              "from": "d2",
              "to": "d4",
              "promotion": null
            },
            "label": "伦敦体系入口",
            "analysis": "先控制 e5",
            "children": []
          }
        ]
      }
    }
  ]
}
```

实际实现时应遵守以下约束：

- `format` 固定，用于排除普通 JSON 或其他应用文件。
- `version` 是文件格式版本，不等同于应用版本。
- 走法保存 `from`、`to`、`promotion` 即可；吃过路兵和王车易位可以由当前局面与走法重新判定，不把可推导值作为合并依据。
- SAN 记谱由规则引擎生成，不作为事实来源，避免规则修正后旧文本阻止导入。
- 树直接嵌套保存，天然保留子分支顺序。
- `currentPath` 保存走法路径而不是内部节点 UUID，以适应当前节点在重新载入时会重建 UUID 的实现。
- 未知字段必须忽略，缺失的可选字段使用默认值，便于向前兼容。

## 4. 文件命名

### 4.1 默认名称

- 单个棋谱：`伦敦体系_2026-10-04.chessnote`
- 全部棋谱：`全部棋谱_2026-10-04.chessnote`

名称处理规则：

1. 去掉首尾空白。
2. 将文件系统不允许的字符 `\\ / : * ? " < > |` 替换为 `_`。
3. 连续空白合并为一个空格。
4. 名称为空时使用 `未命名开局`。
5. 棋谱名称部分最多保留 60 个字符，避免路径过长。

Android 的系统文件创建器负责最终保存位置和同名文件处理。应用只提供建议文件名，不自行扫描目录，也不申请整个存储空间权限。若用户选中的文件提供方允许覆盖，最终覆盖确认交给系统界面完成。

### 4.2 名称不是合并身份

两个都叫“伦敦体系”的棋谱可能完全不同；同一个棋谱也可能已经改名。因此：

- 文档 UUID 用于判断是否可能来自同一份棋谱。
- 名称只用于显示和给出建议，绝不因同名自动覆盖或自动合并。

## 5. 导出交互

### 5.1 单个导出

在棋谱详情页的更多操作中选择 `导出棋谱`：

1. 应用先在内存中生成并校验完整文件。
2. 打开 Android 系统文件创建器，带入建议文件名。
3. 用户选位置并确认后写入。
4. 成功提示：`已导出“伦敦体系”`；失败提示明确原因，不出现英文异常信息。

### 5.2 全部导出

在棋谱列表页选择 `导出全部棋谱`。确认页只显示：

- 棋谱数量。
- 总节点数。
- 说明“导出不会删除或修改应用内数据”。

空列表时禁用该操作，并显示 `还没有可以导出的棋谱`。

### 5.3 一致性

开始生成文件前取得一次数据快照。导出过程中即使用户继续编辑，文件也保持为开始导出那一刻的完整状态，不出现一半新数据、一半旧数据。

## 6. 导入、名称冲突与合并

导入入口放在棋谱列表页，系统文件选择器允许选择一个 `.chessnote` 文件。导入分为“读取校验”“预览选择”“一次性落库”三步；任何一步失败都不改变现有棋谱。

### 6.1 每份导入棋谱的处理选择

| 情况 | 默认处理 | 用户可选项 |
| --- | --- | --- |
| UUID 不存在且名称不重复 | 新建 | 新建、跳过、合并到指定棋谱 |
| UUID 不存在但名称重复 | 新建并改名 | 新建、跳过、合并到指定棋谱 |
| UUID 已存在 | 合并到同一棋谱 | 合并、另存为新棋谱、跳过 |

“替换现有棋谱”不放在第一版。合并失败时仍保留双方，比整份覆盖更符合个人资料工具的安全预期。以后如果加入替换，必须再次确认，并先生成可恢复的本地快照。

### 6.2 新建时的名称冲突

名称冲突只影响显示名称：

- 第一个冲突：`伦敦体系（导入）`
- 继续冲突：`伦敦体系（导入 2）`、`伦敦体系（导入 3）`

应用生成一个新的文档 UUID，避免它以后被误认为原棋谱的同步副本。原始来源 UUID可仅在本次预览中使用，不需要展示给用户。

### 6.3 分支合并算法

节点不依赖内部 UUID，而使用“从根节点开始的完整走法路径”作为逻辑位置：

1. 从双方根节点开始。
2. 同一父节点下走法相同的节点视为同一节点。
3. 只有导入方存在的走法及其子树加入本地树。
4. 双方都存在的节点继续递归合并。
5. 合并完成后保持本地已有分支顺序，新分支追加在其后。

合法性校验与合并同步进行。某一步在其父局面下不合法，则整份文件视为损坏，不做部分导入。

### 6.4 文本冲突

文档名称、文档说明、节点名称、节点分析都可能冲突。第一版使用简单且不会静默决定的规则：

- 一方为空：采用非空值。
- 双方相同：保留一份。
- 双方非空且不同：导入预览中记为一个文本冲突。
- 用户对本次合并统一选择 `保留现有文字` 或 `使用导入文字`。

选择只决定冲突字段；新分支及仅一方非空的字段仍正常合并。预览需显示冲突数量，并明确说明选择会影响哪些文字。第一版不做逐字段冲突编辑，避免合并界面膨胀。

导入完成后提示结果，例如：`新增 1 份，合并 2 份，跳过 1 份；加入 14 个分支，处理 3 处文字冲突。`

## 7. 校验与安全限制

导入前依次检查：

1. 文件可读取且是有效 UTF-8 JSON。
2. `format` 正确，`version` 在应用支持范围内。
3. 文档 ID、名称、根节点和走法字段类型正确。
4. 每条走法在对应局面中合法。
5. 树不存在循环、重复同级走法或不可达节点。
6. 文件大小、文档数、节点数和文本长度不超过安全上限。

建议第一版上限：单文件 20 MB、1000 份棋谱、每份 10000 个节点、单个说明字段 100000 个字符。超过上限时提示 `文件内容过大，无法导入`，不要尝试部分读取后写入。

写入采用全有或全无：先在内存中完成解析、校验和合并，再一次保存新的完整文档列表。原有存储内容必须在保存成功前保持不变。

## 8. 与当前代码的关系

当前 `OpeningRepository` 已经能把文档列表序列化为 JSON，但该 JSON 是内部存储实现，不应直接作为公开导出协议，原因包括：

- 没有格式标识和版本号。
- 节点 UUID 在载入时会被重建，不能作为跨文件合并依据。
- 缺少文件级信息、限制校验和兼容策略。
- 内部字段可以随应用重构变化，公开文件格式需要更稳定。

实现时建议分为四层：

- `ChessNoteCodec`：只负责文件模型与 JSON 的编码、解码、版本迁移。
- `OpeningMergeService`：只负责按走法路径合并并产出预览结果。
- `OpeningRepository`：继续负责应用内部保存；增加一次性保存合并结果的能力即可。
- Compose 页面：负责 Android 文件选择器、预览和用户选择。

不要让导出协议直接调用或改变 `OpeningTree.play()` 的现有交互行为；导入构树可以通过专用构建流程复用规则校验。

## 9. 实施顺序

### 第一阶段：可靠备份

- `.chessnote` 第 1 版格式。
- 导出单个、导出全部。
- 从文件新建导入。
- 格式与合法走法校验。

这一阶段已经解决换手机、手动备份和分享自己棋谱的问题。

### 第二阶段：合并

- UUID 匹配提示。
- 用户指定目标棋谱。
- 按走法路径合并。
- 合并预览与统一文本冲突策略。

### 第三阶段：外部分享

- 导出 PGN。
- 明确标注“用于其他棋类软件，可能不包含应用专有信息”。
- 是否支持 PGN 导入需另行设计，不与无损备份导入混为一谈。

## 10. 验收标准

- 单个和全部导出能通过 Android 系统文件创建器保存，不需要存储权限。
- 将导出的文件重新导入后，文档信息、全部分支、节点名称和分析均保持一致。
- 同名不同 UUID 不会被静默覆盖。
- 同 UUID 的棋谱默认进入合并预览，不会直接覆盖。
- 两棵树合并后包含双方全部走法分支，相同路径只保留一个节点。
- 发生文本冲突时，用户在写入前能够看到数量并选择处理方式。
- 文件损坏、版本过新、包含非法走法或超过限制时，现有数据完全不变。
- 导入导出过程只显示中文且可理解的提示，不暴露异常堆栈或不明英文。
